# 題材企画: `PriorityQueue`を反復してバッチ抽出し、優先度の低いチケットを先に配信する

## 対象

| 項目 | 内容 |
| --- | --- |
| 対象言語 | Java 21 |
| 対象読者 | `PriorityQueue`をバッチ処理やワークキューへ使い、反復順序と取り出し順序を混同しうる中級者 |
| 難易度プロファイル | 実践・上級 |
| 選定理由 | `PriorityQueue`は先頭要素の取得は優先順だが、iterator／streamの走査順は保証しない。バッチ抽出の戻り値、配信済み履歴、待機キューの残状態を分けて観測し、Comparator・キューの内部ヒープ・反復の三つの仮説を比較できる。 |
| 実行基盤 | Maven、Java 21、JUnit Jupiter 5.11.4 |
| フレームワーク非依存性 | 原因は`java.util.PriorityQueue`の反復順序と`poll()`の契約である。HTTP、DI、DB、ORM、外部APIには依存せず、固定のインメモリチケットだけで再現する。 |

## 学習する契約

> 優先度が`1`、`2`、`4`の順に緊急・早期・通常チケットを投入し、二件を配信するとき、優先度`1`と`2`のチケットをこの順に返し、配信済み履歴へ記録し、待機キューには優先度`4`だけを残すべきだが、バグ状態では反復順に選んだ優先度`1`と`4`を配信してしまう。

### 対象の直接原因

`PriorityQueue`を`stream().limit(max)`で走査してバッチを選んでいる。`PriorityQueue`のiteratorおよびSpliteratorは任意の順序で走査してよく、優先順での取り出しは先頭を取得・削除する`poll()`にだけ保証される。

### 対象外

このラボは複数ワーカー、同一優先度の安定順序、スレッド安全性、遅延リトライ、優先度の動的変更、永続キュー、分散配送を扱わない。異なる優先度を持つ三件の単一スレッド・インメモリキューから、先頭二件を取り出すという狭い規則だけを扱う。

## 再現設計

| 要素 | 決定 |
| --- | --- |
| 公開境界 | `TicketDispatchService#dispatchBatch(int)`、`dispatchedTickets()`、`waitingTickets()`。 |
| 入力・初期状態 | 空のサービスへ`urgent`（優先度1）、`normal`（優先度4）、`soon`（優先度2）をこの順に投入し、二件を配信する。 |
| Redの観測 | 直接の戻り値が`[urgent, soon]`であるべきだが、バグ状態では`[urgent, normal]`となる。 |
| 最終観測 | 配信済み履歴が`[urgent, soon]`であり、待機キューが`[normal]`であることを別々に検証する。 |
| 決定性 | 時刻、乱数、並行実行、`sleep`、外部I/Oを使わず、固定の優先度とインメモリ状態だけを使う。 |
| 固定状態の検証コマンド | `mvn --batch-mode clean test` |
| バグ状態の確認コマンド | `git checkout <bug-commit>`後に`mvn --batch-mode test -Dtest=TicketDispatchServiceTest` |

## 仮説

| 仮説 | どう検証または除外するか |
| --- | --- |
| A: チケットのComparatorが優先度を逆順に比較している | `poll()`を使った同じ三件の取り出し順を観測する。 |
| B: 投入処理がチケットをキューへ正しく登録していない | 待機キューに三件がすべて存在すること、優先度`1`のチケットが先頭であることを対照観測する。 |
| C: iterator／streamの走査順を優先順と誤認している | 同じキューのstream順とpoll順を別々に観測する。 |

## 予定する履歴

| 順序 | コミットの目的 | 期待する状態 |
| --- | --- | --- |
| 1 | 優先キューのバッチ抽出順序失敗を再現する | 対象テストが`[urgent, soon]`期待・`[urgent, normal]`実際のアサーション差分で失敗する。 |
| 2 | 優先キューから優先順にバッチ抽出する | 同じ検証が成功し、全体も成功する。 |
